## Context

The PageIndex ingestion pipeline currently processes documents sequentially with aggressive memory isolation (subprocess-per-document), a stale memory admission gate, and a hard worker concurrency ceiling of `MAX_JOBS=1`. For small corpora (16 documents), end-to-end ingestion takes materially longer than the underlying extraction time warrants. The bottlenecks compound: each document spawns a fresh Python process (model-loading overhead repeated), ~~recovery attempts run serially even when independent~~ recovery methods are slower than they need to be (they must stay sequential — shared `ExtractionState`, D5; **Amendment 2026-09-24, Iter 7**), and the memory admission floor (`MEM_ADMISSION_FLOOR_BYTES ≈ 2.2 GiB`) was calibrated for local Docling — not the remote Docling service that is now the default path.

Separately, the raw markdown/text extracted during ingestion is discarded after tree construction. The storage layer has a `save_raw` function (`storage/documents.py:838-854`) with ~~**zero callers** — it was scaffolded but never wired~~ **(Amendment 2026-09-24, Iteration 5): two callers, both persisting the uploaded file bytes, not the extracted markdown — `asyncio.to_thread(save_raw, doc_id, filename, file_bytes)` at `client/indexer.py:2226` (flat) and `:2407` (tree). The extracted markdown itself is never persisted.** Users have no way to inspect the pre-tree-construction extraction output, making quality diagnosis harder and preventing downstream consumers from accessing the unprocessed text.

~~These two concerns — throughput and raw output visibility — are coupled: persisting raw output before tree construction enables re-processing without re-extraction (the most expensive stage), which is itself an acceleration strategy.~~ **(Amendment 2026-09-24, Iteration 6):** The two concerns are related, not coupled. Persisted extraction output enables a diagnostic dry-run replay of tree construction, gating and verdict without re-extraction ([D4](#decision-summary)); it does not shorten ingestion. "Extraction is the most expensive stage" is unmeasured: `metrics/definitions.py` has only end-to-end `UPLOAD_DURATION` and per-call `LLM_DURATION`, and tree construction itself makes one LLM summary call per node over 200 tokens plus a document-description call (`_run_md_to_tree`, `client/indexer.py:2912-2968`). Task 1.5 adds the extraction / tree-build split.

Prior work: [[RFC-043]] (OCR/garble hardening), [[RFC-044]] (recovery dispatch), [[RFC-046]] (OCR attribution). `docs/PARALLEL_INGESTION.md` documents the parallelism architecture and recommends admission-gate tuning as the #1 throughput lever.

## Goals

- **G1**: **Current contract (2026-09-24, Iter 8):** reduce end-to-end wall-clock time for ingesting the current 16-document corpus under remote Docling by **≥30%** (median of two runs per arm). The measurement protocol is fixed: ingest through `make ingest` (the worker path, `scripts/remote_ingest_test.py` → `POST /upload/files`), because D1/D2 act only on the arq worker; `preprocess_client.py` runs with its own `PREPROCESS_CONCURRENCY` (default 1) and no admission gate, so it would show no gain. KEDA is pinned to one worker replica (NG3), both arms use the same `.env.active` (same Docling endpoint, same LLM endpoint and model), and each arm runs twice; the medians are compared. The per-stage split from Task 1.5 is reported. The baseline (Task 9.1) runs right after Task 1.5 and before Tasks 1.1-1.3, so no D1-D3 behaviour is live in it. D5 is judged separately: a lower recovery-stage p50 (Task 1.5 histogram, `stage="recovery"`) on the corpus documents that enter recovery. It is not part of the G1 gate.

## Non-Goals

- **NG1**: Replacing subprocess isolation with in-process threading. The memory-safety guarantee of process isolation is load-bearing for OOM protection and will not be removed.
- **NG2**: Parallelizing stages within a single document's `_run_stages` pipeline. Stage interdependencies (each stage mutates the markdown string) make this unsafe without a major redesign.
- **NG3**: Horizontal auto-scaling beyond KEDA's current 1↔2 replica range. Infrastructure scaling is a deployment concern, not a pipeline code change.
- **NG4**: Changing the Docling extraction engine or adding new converters. This RFC optimizes the pipeline around existing converters.
- **NG5 (Added: 2026-09-24, Iteration 6)**: Re-processing over HTTP/arq, and re-persisting a document from cached extraction (in place or under a new `doc_id`). D4 is a CLI dry run only. `POST /upload/files` takes file bytes, so a `from_raw` form flag would force a re-upload; a re-persist needs doc-identity, route-change cleanup and reject-deletion rules. Deferred to a follow-up RFC if needed.
- **NG6 (Added: 2026-09-24, Iteration 6)**: Replaying normalization stages. The cached text is post-stages and post-recovery (R3 AC1), and two of the three extraction stages need the PDF — `document_level_text_fallback` and `splice_landscape_fallback` are partials over `pdf_path` (`converters/pipeline.py:774-784`). Checking a stage change still needs a full re-extraction.

## Requirements

### Requirement 1: Route-Aware Admission Gate

**User Story:** As a platform operator, I want the memory admission gate to use different thresholds for local vs. remote Docling, so that remote-Docling workers can safely process more concurrent jobs.

**Design (Added: 2026-09-24, Iter 8):** [§1 Admission Gate](../designs/design-rfc050-pipeline-acceleration-raw-export.md#1-admission-gate-memory_admissionpy) · [Property 1](../designs/design-rfc050-pipeline-acceleration-raw-export.md#property-1-admission-gate-route-selection)

#### Acceptance Criteria

1. WHEN `DOCLING_SERVICE_URL` is set (remote mode), THE Admission Gate SHALL pass `MEM_ADMISSION_FLOOR_REMOTE_BYTES` (default: 800 MiB) as the `floor` parameter to `_has_headroom` in `memory_admission.py`, instead of the default `MEM_ADMISSION_FLOOR_BYTES` (2.2 GiB). **(Amendment 2026-09-24: `_has_headroom` already accepts a `floor` param — leverage existing interface)** **(Amendment 2026-09-24, Iter 8):** `_has_headroom(available, floor=MEM_ADMISSION_FLOOR_BYTES)` (`src/pageindex_mcp/memory_admission.py:49`) already takes `floor`; the change is a new `floor` parameter on `wait_for_memory` (`:72-99`), which today calls `_has_headroom(available)` at `:86` without it. Both constants live in `src/pageindex_mcp/memory_admission.py` (`MEM_ADMISSION_FLOOR_BYTES` at `:23`).
2. WHEN `DOCLING_SERVICE_URL` is unset (local mode), THE Admission Gate SHALL continue using `MEM_ADMISSION_FLOOR_BYTES` unchanged.
3. THE worker SHALL log the active admission threshold at startup, including which mode (local/remote) was selected.

### Requirement 2: Configurable Worker Concurrency

**User Story:** As a platform operator, I want to raise `MAX_JOBS` above 1 for remote Docling without editing source code, so that multiple documents process in parallel on a single worker replica.

**Design (Added: 2026-09-24, Iter 8):** [Property 1](../designs/design-rfc050-pipeline-acceleration-raw-export.md#property-1-admission-gate-route-selection) · [Property 6](../designs/design-rfc050-pipeline-acceleration-raw-export.md#property-6-max_jobs-ceiling)

#### Acceptance Criteria

1. WHEN `DOCLING_SERVICE_URL` is set AND `MAX_JOBS` is not explicitly configured, THE worker SHALL default to `MAX_JOBS=2`.
2. WHEN `MAX_JOBS` is explicitly set, THE worker SHALL respect the explicit value regardless of Docling mode.
3. THE worker SHALL enforce `MAX_JOBS ≤ 4` as a hard ceiling, logging a warning if a higher value is requested.
4. THE worker SHALL expose the active `MAX_JOBS` value as a Prometheus gauge `pageindex_worker_max_jobs`.

### Requirement 3: Raw Output Persistence

**User Story:** As a document analyst, I want to access the raw markdown extracted from a document before tree construction, so that I can diagnose quality issues and build downstream processing pipelines.

**Design (Added: 2026-09-24, Iter 8):** [§2 Raw Output Persistence](../designs/design-rfc050-pipeline-acceleration-raw-export.md#2-raw-output-persistence-save_raw) · [Property 2](../designs/design-rfc050-pipeline-acceleration-raw-export.md#property-2-raw-output-persistence-completeness) · [Property 3](../designs/design-rfc050-pipeline-acceleration-raw-export.md#property-3-erasure-cascade-completeness) · [Property 3a](../designs/design-rfc050-pipeline-acceleration-raw-export.md#property-3a-rejected-output-is-never-served-added-2026-09-24-iteration-5) · [Property 3b](../designs/design-rfc050-pipeline-acceleration-raw-export.md#property-3b-quarantine-expires-within-30-days-added-2026-09-24-iter-8)

**Current contract for AC1/AC2 (2026-09-24, Iter 8):** the extracted markdown and its state sidecar are written at four sites, each guarded by `state.md_content is not None` and each best-effort (a failed write is logged and never blocks the route).
- **Persisted (TREE and FLAT):** in `_persist_tree_result` (`client/indexer.py:2407`) and `_persist_flat_result` (`:2226`), after the existing `save_raw(doc_id, filename, file_bytes)`, write `uploads/<doc_id>/<filename>.extracted.md` and `uploads/<doc_id>/<filename>.extracted.state.json`, both via `save_raw`.
- **Rejected:** at the `flat_garble_unrecovered` branch inside `_persist_flat_result` (`:1924-1933`) and at `case (False, Route.REJECT)` in `index()` (`:2762-2787`, for every reject reason), write `quarantine/<sha256>.extracted.md` and `quarantine/<sha256>.extracted.state.json` via `save_quarantine_extracted(sha256, md, state)`. Both objects expire after 30 days with the rest of `quarantine/` (AC6).
- **No write** for `.md`/`.markdown`/`.txt` inputs, the LibreOffice `page_index` route or the all-converters-failed `page_index` fallback, where `md_content` is `None`.

### Requirement 4: Re-Processing From Raw Cache

**User Story:** ~~As a platform operator, I want to re-run tree construction on a document without re-extracting from PDF, so that pipeline improvements can be validated faster.~~ **(Amendment 2026-09-24, Iteration 6):** As a platform operator, I want to replay a stored or rejected document's cached extraction through tree construction, gating and the verdict — without re-extracting and without changing anything stored — so that I can see why it failed and check a tree/gate/verdict change against it.

~~2. THE `--from-raw` path SHALL still run all normalization stages, tree construction, validation, and quality gating.~~

1. WHEN an operator runs `preprocess_client.py --from-raw --doc-id <doc_id>` (persisted document) or `--from-raw --sha256 <sha256>` (rejected document), THE CLI SHALL replay the cached extraction — `uploads/<doc_id>/<filename>.extracted.md` or `quarantine/<sha256>.extracted.md` — through tree construction (`_run_md_to_tree`), `prepare_tree`, `validate_tree`, `finalize_gate_and_route` and the route's verdict, without running any converter and without the hash-cache dedup early return.
2. THE replay SHALL NOT re-run normalization stages. It SHALL restore converter state from the state sidecar (R3 AC5); when the sidecar is missing (documents persisted before it shipped), it SHALL use defaults and mark the report `approximate`, listing the missing fields.
3. THE replay SHALL be a dry run: zero writes to MinIO, Redis (document cache, hash cache, reconcile-etag) and the Postgres registry. **(Amendment 2026-09-24, Iter 7):** in the child, writes go to an in-memory read-your-writes overlay over the MinIO and Redis clients, so the persist methods' own read-after-write checks pass; the registry is written only by the parent, which skips the upsert and the metric mirror during a replay. **(Amendment 2026-09-24, Iter 8):** the overlay is fail-closed. It emulates a named set of client methods, and any other method raises `ReplayWriteBlocked` instead of reaching a store (design §3). In the parent, the replay makes no `registry_mirror` Redis writes (`_mirror_bridged_set`, `_mirror_bridged_incr`) and never calls `_upsert_registry_row` or `save_doc_meta`. In-process Prometheus gauges are exempt: they are not a store. ### Requirement 5: Recovery Method Optimization

**User Story:** As a platform operator, I want the slowest recovery methods profiled and optimized, so that recovery overhead is reduced without breaking the sequential ordering invariant.

**(Amendment 2026-09-24, Iteration 2): Redefined from "Recovery Loop Parallelization" to "Recovery Method Optimization". Deep review found all 8 recovery methods mutate shared `ExtractionState` — sequential ordering is a load-bearing correctness invariant (each method's eligibility depends on state left by prior methods). Parallelization via `asyncio.gather` is architecturally infeasible without speculative execution (a fundamentally different design). Scope changed to profiling and optimizing individual methods.**

**Design (Added: 2026-09-24, Iter 8):** [Property 5](../designs/design-rfc050-pipeline-acceleration-raw-export.md#property-5-recovery-optimization-equivalence)

#### Acceptance Criteria

1. EACH recovery method in `RecoveryMixin` (`client/recovery.py`) SHALL be profiled under representative documents to identify the slowest methods.
2. THE slowest recovery methods SHALL be optimized (e.g., reduce redundant reconversions, cache intermediate results) without altering the sequential dispatch order.
3. THE sequential GateSpec dispatch loop in `index()` SHALL NOT be restructured — the ordering invariant must be preserved.
4. THE pipeline SHALL log per-method wall-clock time for observability.

## Risks

1. **Raising `MAX_JOBS` may increase memory pressure on the worker host.** Mitigation: the remote-Docling admission floor (800 MiB) is conservative; actual RSS per job is ~200-400 MiB. Monitor via Prometheus and reduce if needed.
2. **Raw output persistence ~~doubles~~ roughly triples the `uploads/` MinIO writes per document (upload + `.extracted.md` + `.extracted.state.json` — Amendment 2026-09-24, Iter 7).** Mitigation: raw markdown is typically 10-100 KB per document — negligible compared to figure storage.
3. **Recovery optimization may alter method behavior subtly.** Mitigation: property test confirms optimized methods produce identical output to baseline for representative documents. Sequential ordering invariant preserved — no architectural change to the GateSpec dispatch loop.
4. **`--from-raw` may mask extraction regressions if operators always use cached raw.** Mitigation: the flag is opt-in and provenance logging makes the source visible. **(Amendment 2026-09-24, Iteration 6):** moot for stored output — the replay writes nothing. Residual: it reads post-stages text, so it cannot show the effect of a normalization-stage change (NG6), and for documents persisted before the state sidecar it runs on defaults (report marked `approximate`).
5. **(Amendment 2026-09-24, Iter 8): resolved — D6 reversed; quarantine expires after 30 days (R3 AC6).** Residual: a rejected document can be replayed only within 30 days of rejection; after that the replay exits `no_raw_cache`. If the lifecycle rule is missing from a bucket (for example, a fresh MinIO), the Task 3.6 check fails. ~~**(Added: 2026-09-24, Iteration 5) Quarantine retention is unbounded after D6.** A document rejected once and never re-ingested keeps its quarantine objects (now including the full extracted text) until someone erases them. Mitigation: HR2 erasure is intact on request (`delete_doc` via `ctx.sha256`; `erase_quarantine(sha256)` with the sha256 surfaced in the rejected job's status); `clear_quarantine` removes them on a later successful persist; objects are small (10-100 KB markdown). Residual: for a PII corpus, extracted text of rejected documents persists until an explicit DSR — the operator must look it up by sha256.~~
6. **(Added: 2026-09-24, Iteration 6) A missed write path would let a dry run change stored state.** The persist methods write MinIO objects and figures, upsert the registry row, touch the document and hash caches, and clear quarantine. Mitigation: the barrier sits at the three store clients in the replay child, not at individual call sites, and the integration test asserts zero executed mutating calls on each. Recovery during a replay makes the same LLM/OCR calls as a normal ingest, through the same routing (HR3), so it costs the same. **(Amendment 2026-09-24, Iter 7):** the barrier is an in-memory read-your-writes overlay over the clients returned by `storage.minio_ops.get_minio()`, `cache.get_cache_redis()` and `cache.get_async_redis()` — the persist path reads back its own writes (`_confirm_write_visible`, the verdict sidecar), so "record and drop" would fail. The registry is written only in the parent (`_upsert_registry_row`), as is the `_mirror_bridged_set` Redis write; `_replay_one` skips both. Residual: a new store client added later outside these three accessors would bypass the overlay — the Property 4a test (byte-identical stores before and after) catches that. **(Amendment 2026-09-24, Iter 8):** "wraps the clients returned by the accessors" is superseded. The replay child sets the singletons `minio_ops._minio_client`, `cache._redis_sync` and `cache._redis_async` directly, through a context manager that restores them. The overlay is fail-closed: a method outside its emulated and read-only pass-through lists raises `ReplayWriteBlocked`, so a missed method (the Iter 7 list lacked `setex`, `hdel`, `eval`, `incr`, `hgetall`, `list_objects` and `fget_object`) becomes a test failure, not a real write.
7. **(Added: 2026-09-24, Iter 7) Replay spends LLM tokens.** The barrier blocks writes, not LLM calls: every replay makes `_run_md_to_tree`'s per-node summary calls, and on the flat route `_generate_flat_doc_description`, plus any recovery calls. Mitigation: the operator runs it one document at a time, the report counts the calls, and the calls go through the normal routing (HR3). Replaying a whole corpus costs about as much as the tree-build stage of re-ingesting it. **(Amendment 2026-09-24, Iter 8):** the flat-route VLM garble fallback (`vlm_extract_markdown`) is also an LLM call. It counts as recovery (R4 AC4): skipped without an original or under `--no-recovery`, and counted in the report when it runs.
8. **(Added: 2026-09-24, Iter 8) A replay on the operator's host could send PII to a non-ZDR endpoint (HR3).** The replay uses the operator's `.env.active`, not the worker's. Mitigation: R4 AC9 prints `OPENAI_BASE_URL` and the resolved tier, and refuses a non-ZDR tier unless `--allow-non-zdr` is given.
9. **(Added: 2026-09-24, Iter 8) Replay leaves document copies on the operator's host (HR2).** Mitigation: R4 AC8 uses a `TemporaryDirectory` context manager with cleanup on every exit path, and R4 AC10 marks the report as holding document content, with `--no-text` for structure only. Residual: an operator who redirects a full-text report to a file owns that copy.

## Consequences

- Worker throughput increases proportionally to `MAX_JOBS` (expected 2-3x for remote Docling).
- Raw output files add ~1-5 MB total storage per corpus (negligible).
- ~~The `--from-raw` path creates a fast iteration loop: change normalization/tree logic → re-process from cached raw → validate — without waiting for PDF extraction.~~ **(Amendment 2026-09-24, Iteration 6):** The replay gives a diagnosis loop: change tree-building, gate or verdict logic → replay stored and rejected documents → compare with what is stored — without Docling. It does not cover normalization-stage changes (NG6), still pays for the LLM summary calls, and changes nothing stored.
- **(Added: 2026-09-24, Iter 7)** Effort rises to ~~32.5-36.5h~~ (from 31-35h): the D4 write barrier becomes an in-memory read-your-writes overlay (+1.5h). The state sidecar (Task 3.1b) stays in P0 by decision. **(Amendment 2026-09-24, Iter 8):** **37-41h**. The TTL rule adds 0.5h; the fail-closed overlay spec adds a net 2.5h; the HR2/HR3 replay safeguards add 0.5h; two runs per arm add 1h.
- **(Added: 2026-09-24, Iter 7)** The MCP surface grows from five to six query tools (`get_raw_output`); `DESIGN.md` §MCP Tool Contracts is updated with it (Task 3.4). ~~Every test-adding task bumps `tests/TEST_BUDGET.baseline`;~~ RFC-051 lowers it, and whichever RFC lands second rebases. **(Amendment 2026-09-24, Iter 8):**
- `DESIGN.md` lists 5 registered and 2 planned tools; `get_raw_output` is the sixth registered one.
- `FROZEN_SURFACE["tools"]` (`scripts/gates/source_invariants.py:501-507`) and `FROZEN_SURFACE["metrics"]` are updated in the same commits as Tasks 3.4 and 1.5.
- The TEST_BUDGET baseline is bumped only when the collected count leaves the ±15 band, and every commit must pass `test_budget.sh`.
- Right-to-erasure cascade grows by one path ~~(`*.raw.md`)~~ **(Amendment 2026-09-24, Iteration 5):** per store — `uploads/<doc_id>/*.extracted.md` needs no new manifest entry (prefix delete), and `quarantine/<sha256>.extracted.md` adds a third key to the existing quarantine step and to `erase_quarantine` — **(Iteration 6)** and `quarantine/<sha256>.extracted.state.json` a fourth; its `uploads/` twin is covered by the prefix delete.
- ~~**(Added: 2026-09-24, Iteration 5)** RFC-049's 30-day quarantine TTL is superseded (D6); quarantine is bounded by clear-on-success and on-demand erasure only.~~ **(Amendment 2026-09-24, Iter 8):** RFC-049's 30-day quarantine TTL stands and is implemented here (D6, Task 3.6). Quarantine is bounded by the TTL, clear-on-success and on-demand erasure, as HR5 requires.
- Future RFCs can build on raw output for alternative processing pipelines (e.g., direct RAG without tree construction).
