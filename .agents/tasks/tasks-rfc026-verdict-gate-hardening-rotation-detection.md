## Overview

This plan implements five of the six RFC-026 fix dimensions across three batches — [D6](../rfcs/026-run9-verdict-gate-hardening-and-rotation-detection.md#out-of-scope) (Latin-gibberish CMap detection) is explicitly **deferred** and excluded from this plan per the RFC's own scope note. Batch 0 lands the three verdict-gate fixes that share `helpers.py` — [D0](../rfcs/026-run9-verdict-gate-hardening-and-rotation-detection.md#d0--hard-fail-floor-for-zero-content-documents) (zero-content FAIL floor), [D1](../rfcs/026-run9-verdict-gate-hardening-and-rotation-detection.md#d1--image-enrichment-promoted-volume-floor) (image-enrichment volume floor), and [D5](../rfcs/026-run9-verdict-gate-hardening-and-rotation-detection.md#d5--validate-tree-garble-check-ordering) (garble-check reordering in `validate_tree()`) — batching them avoids merge conflicts and matches the RFC's own priority ordering (D0, D1, D5 are the three highest-priority, lowest-complexity items). Batch 1 lands [D2](../rfcs/026-run9-verdict-gate-hardening-and-rotation-detection.md#d2--page-level-rotation-detection) (page-level rotation detection) in `converters.py`, independent of the verdict-gate logic and the largest single change in the RFC. Batch 2 lands [D3](../rfcs/026-run9-verdict-gate-hardening-and-rotation-detection.md#d3--hysteresis-preservation-across-reingestion-wipe) (hysteresis snapshot across reingestion wipe, `storage.py`) and [D4](../rfcs/026-run9-verdict-gate-hardening-and-rotation-detection.md#d4--scoring-harness-stage-2-guard-fix) (scoring-harness Stage 2 guard fix, `.claude/workflows/corpus-ingest-score.js`) — these are independent of each other and of Batches 0-1, and are grouped together as the two remaining lower-priority items. Per explicit user directive, **no task in this plan performs ingestion, reingestion, or corpus verification** — those steps belong to the corpus quality cycle, which runs separately after this plan lands. Every task ends at a `uv run pytest` (or, for D4, a harness-level JS assertion) unit/integration boundary.

## Notes

- [D6](../rfcs/026-run9-verdict-gate-hardening-and-rotation-detection.md#out-of-scope) (Latin-gibberish CMap detection for Haftpflicht-class docs) is **explicitly deferred** per the RFC's own [Priority Order](../rfcs/026-run9-verdict-gate-hardening-and-rotation-detection.md#priority-order) item 7 ("deferred if scope tight") and is excluded from this plan entirely — no task, test, or checkpoint in this document references it as in-scope work.
- Per explicit user directive: this plan contains **no ingestion, reingestion, or "verify with corpus" tasks**. The corpus quality cycle (separate skill/process) handles ingestion and scoring after this plan's code changes land; do not add such a step to any batch or checkpoint here even if a future editor is tempted to mirror the RFC-025 tasks file's Batch 4 pattern.
- [Task 1.1](#11-zero-content-fail-floor)'s [D0](../rfcs/026-run9-verdict-gate-hardening-and-rotation-detection.md#d0--hard-fail-floor-for-zero-content-documents) FAIL floor must run before [Task 1.2](#12-image-enrichment-volume-floor)'s [D1](../rfcs/026-run9-verdict-gate-hardening-and-rotation-detection.md#d1--image-enrichment-promoted-volume-floor) promotion-floor check in the final `classify_verdict()` control flow — the RFC's ordering requirement (D0 before `image_enrichment_promoted`, line 1198) is load-bearing: it prevents the D1 char-floor branch from ever seeing a `total_chars == 0` document, which must always resolve to `zero_content`, not `image_enrichment_promoted_below_char_floor`.
- [Task 2.2](#22-rotation-aware-converter-integration)'s [D2](../rfcs/026-run9-verdict-gate-hardening-and-rotation-detection.md#d2--page-level-rotation-detection) coordinate transform is scoped to the docling markdown-extraction path only. It must not alter the existing D6 rotation-zeroing logic at the Tesseract OCR-crop site (`converters.py` ~lines 1744-1755) — that is a different call path solving a different problem (crop orientation, not text-block coordinate mapping) and any regression there would reopen a previously-fixed defect.
- [Task 3.1](#31-hysteresis-verdict-snapshot)'s snapshot is strictly a fallback: when both an individual `processed/<doc_id>.meta.json` sidecar and the `processed/_prior_verdicts.json` snapshot could answer a `find_prior_verdict()` query, the individual sidecar must win. This preserves the existing RFC-025 [Design Property 1: Prior-verdict hysteresis anchoring](../designs/design-rfc025-run8-verdict-hysteresis-and-recovery-coverage.md#property-1-prior-verdict-hysteresis-anchoring-d0) behavior for the common case and only changes behavior for the post-wipe case where no individual sidecar exists yet.
- Every fix in this plan should ship with a named env var defaulting to the fixed/new behavior ([Task 1.2](#12-image-enrichment-volume-floor)'s `MIN_IMAGE_PROMOTED_CHARS`, [Task 2.2](#22-rotation-aware-converter-integration)'s `PAGE_ROTATION_DETECTION_ENABLED`) where a rollback lever makes sense; [Task 1.1](#11-zero-content-fail-floor) and [Task 1.3](#13-validate-tree-garble-reorder) are pure Hard-Rule-5 correctness fixes with no safe "disabled" state and intentionally ship without a toggle; [Task 3.1](#31-hysteresis-verdict-snapshot) and [Task 3.2](#32-scoring-harness-structured-output) are additive/fallback-only and process-tooling fixes respectively, neither needs a toggle.
- Tests in [Task 1.4](#14-unit-tests-batch-0), [Task 2.3](#23-unit-tests-batch-1), and [Task 3.3](#33-unit-tests-batch-2) are required, not optional, given the [CLAUDE.md Hard Rule 5](../../CLAUDE.md#hard-rules) quality-gate implications of D0, D1, and D5 — do not skip them for a faster landing.
