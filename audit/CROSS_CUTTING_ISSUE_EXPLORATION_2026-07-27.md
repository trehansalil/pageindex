## Issue 2: P0b — Page-Coverage Filter Sub-60% Gap

**Status: D1 fix IMPLEMENTED in working tree, UNCOMMITTED.**

### The 0.6 threshold (D0)

`converters.py:1470-1473`:
```python
_PICTURE_PAGE_COVERAGE_THRESHOLD = os.getenv("PICTURE_PAGE_COVERAGE_THRESHOLD", "0.6")
...
page_area = page.rect.width * page.rect.height
if page_area > 0 and (rect.width * rect.height) / page_area > _PICTURE_PAGE_COVERAGE_THRESHOLD:
    continue  # skip — treated as full scanned page, not a chart
```

Only filters pictures >60% of page area. Any chart/infographic below that threshold sails through to cropping + Tesseract OCR, regardless of whether Docling's text layer already extracted the labels cleanly.

### The D1 fix (uncommitted working tree)

`converters.py:1474-1478`:
```python
# D1 (RFC-018): skip per-picture OCR when clean text already exists
clip_text = page.get_text("text", clip=rect).strip()
if len(clip_text) > _PICTURE_OCR_MIN_CHARS:   # 20
    continue
```

Uses PyMuPDF's native text extraction scoped to the picture's `fitz.Rect` — independent probe for a vector text layer, not trust in Docling's classification.

### Why sub-60% regions bypassed the old filter

D0 alone answers "is this basically the whole page" (full-page scan detection), not "does this region already have machine-readable text." A chart at 15% page area with clean vector axis labels had no gate stopping OCR from re-deriving that text via 300-DPI crop -> Tesseract, which garbles small-font numerals.

### Before/After

**Before**: `> [Chart text]: 20l9 2O2O 202l Revenoe` spliced in, duplicating and corrupting clean body text.
**After**: No chart-text splice; clean body text `2019 2020 2021 Revenue` from Docling's export stands alone.

## Issue 3: Garble-Gate Latin-Gibberish Blind Spot

**Status: NOT STARTED. Requires new heuristic.**

### Current implementation

`_is_garbled_blob()` (`helpers.py:568-601`) checks in order:
1. Empty text
2. `\x00`/`�` replacement chars
3. `GLYPH<` markers
4. Control-char ratio >5%
5. **PUA ratio >3%** (`helpers.py:583-586`)
6. Digit ratio >60% (blobs >500 chars)
7. Single-token repetition >30%

Plus `_has_sparse_mojibake()` (`helpers.py:622-634`, RFC-015 D8): regex-matches glued Arabic-Latin-Arabic / Latin-Arabic-Latin fragments (`_MIXED_SCRIPT_RE`), flags >2% token-match ratio.

### What it misses

**Valid-looking, space-separated Latin gibberish** — "de", "Bab", "rel igh", "foal!", "pred". This text is:
1. Not PUA (real ASCII/Latin letters)
2. Not glued to Arabic (has whitespace, so `_MIXED_SCRIPT_RE` never matches)
3. Not digit-heavy
4. Rarely hits 30% single-token repetition (OCR noise varies)

Affected docs: MOU MOHRE, qarar 106/2022, warid 597 — all Arabic-source PDFs where Tesseract `ara` mis-recognizes low-quality scan regions as Latin script.

### Fix recommendation: Approach C (script-context dictionary-ratio)

```python
# After existing checks, before return False:
if expected_script == "Arab" and _latin_token_ratio(text) > 0.4:
    latin_tokens = _LATIN_TOKEN_RE.findall(text)
    if len(latin_tokens) > 5:
        nonsense = sum(1 for t in latin_tokens if t.lower() not in _COMMON_WORDS)
        if nonsense / len(latin_tokens) > 0.7:
            return True  # Latin gibberish in Arabic context
```

- `expected_script` from majority Unicode block of node/page
- `_COMMON_WORDS`: ~200-entry English+German stopword frozenset (zero dependency)
- Matches existing heuristic style (additive-OR, cheap ratio checks)

### Alternatives rejected

- **(A) n-gram log-likelihood**: heavier calibration, reference tables to ship
- **(B) LM perplexity**: conflicts with CPU-cost precedent (Granite-258M user-locked rejection 2026-06-12)

## Issue 4: Unresolved `<!-- image -->` Markers in Output

**Status: NOT STARTED. ~15 LOC fix.**

### Root cause

When D0 skips a region for coverage, `_recover_picture_results` (`converters.py:~1620`) dense-fills with empty `PictureResult()`. `splice_figure_markers` then hits:
```python
if not (ocr or desc or result.get("png_bytes")):
    return m.group(0)  # keeps "<!-- image -->" verbatim
```

The coverage filter suppresses wasted OCR but never closes the marker-removal loop. The neutral-marker fallback predates D0 and was correct then — an empty result meant "recovery attempted, found nothing." D0 introduced a second meaning ("recovery deliberately declined") that the fallback cannot distinguish.

### Fix

Tag deliberate skips in `_recover_picture_results`:
```python
recovered.get(i, PictureResult(skipped_reason="page_coverage"))
```

Branch in `splice_figure_markers`:
```python
if not (ocr or desc or result.get("png_bytes")):
    if result.get("skipped_reason") or result.get("decorative"):
        return ""  # deliberate skip — strip marker
    return m.group(0)  # genuine failure — keep for debugging
```
